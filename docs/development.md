# Development & deployment

This document details the local setup, the tests and the scripts behind the
[README](../README.md)'s Getting started and Scripts sections; [Architecture](architecture.md)
describes what the scripts run, and [Connecting agents](connecting-agents.md) walks through both
operators' sessions when a card agent is connected. Each script's header comment is its full
documentation, and `--help` prints it.

## Working copy location

Keep the checkout on the WSL ext4 filesystem (`~/projects/python/home-finance-agent`) rather than
under `/mnt/c`. WSL reaches Windows drives through a file-sharing protocol that makes every file
open a round trip to the Windows side, and the virtualenv installs, `npm ci` and the test runs
open thousands of files.

## Frontend

`deploy.sh` serves the built page from the manager image, through the edge at
http://localhost:8010. For work on the page, `npm run dev` in `frontend/` serves it with hot
reload at http://localhost:5173 and proxies `/api` and `/health` to http://localhost:8010, so the
stack must be up. Signing in there needs `http://localhost:5173` as a further authorized
JavaScript origin of the Google client ([Sign-in](sign-in.md#setting-up-google)).

## Configuration

`./scripts/init-env.sh` creates the gitignored `secrets.sh`, `params.sh` and `aws-config.sh`
under `scripts/lib/` from [secrets.example.sh](../scripts/lib/secrets.example.sh),
[params.example.sh](../scripts/lib/params.example.sh) and
[aws-config.example.sh](../scripts/lib/aws-config.example.sh), keeping a file that already
exists; each setting's comment says what it holds and whether it is required. It also creates
the empty card-agent registries and `config/budget.yaml`, below. `deploy.sh` runs it first on
every run, and stops with a list of every setting it needs that is still blank.

- `secrets.sh` — the database password, generated by `init-env.sh`, the database URL built from
  it, and the model provider's API key.
- `params.sh` — this deployment's own settings that are no secret: `LLM_MODEL`,
  `GOOGLE_CLIENT_ID` ([Sign-in](sign-in.md#setting-up-google) sets up the Google client) and
  the license contact.
- `aws-config.sh` — the access key pair and region of the AWS account `deploy.sh --ec2`
  deploys to; a machine that deploys only locally leaves it unfilled.

Every other setting is committed in [stack-params.sh](../scripts/lib/stack-params.sh): the
ports, the database name, the EC2 stack's names and the optional keys at their defaults. The
manager refuses to start while `LLM_MODEL`, `GOOGLE_CLIENT_ID` or `LLM_API_KEY` is blank. An edit
to any of the three files takes a `deploy.sh` run.

Beside the settings files, two gitignored files belong to the person running the stack:

- `backend/card-agents.yaml` and `backend/card-agents.ec2.yaml` — the card agents the manager
  calls on this machine and on the EC2 instance, with the secrets they issued to it;
  `tools/add-card-agent.sh` writes them ([Connecting a card agent](#connecting-a-card-agent)).
  An empty registry means no card agents: the manager runs and the page says so.
- `config/budget.yaml` — the monthly limit per category, started from the committed
  `config/budget.example.yaml`; the image bakes it in, so an edit takes a `deploy.sh` run.

A script that loads a settings file first stops if git would track it, or a tracked file holds
one of its secrets or email addresses, the license contact of `params.sh` excepted. It also
sets `core.hooksPath` to `.githooks`, whose `pre-commit` hook makes the same check on every
commit's staged changes.

The scripts export the three files into their shell before calling Compose, so a bare
`docker compose` call has no settings. The files hold the host form of `DATABASE_URL`; Compose
overrides it with the in-network address. Host commands (pytest, uvicorn) run from the repo
root, because the manager reads the settings files by their path from the working directory.

## Backend tests

[`test.sh`](../scripts/test.sh) is the whole quality gate. It runs the backend and the frontend
by default, or the targets named: `backend` runs the scripts' syntax check and their shell tests
under `scripts/tests/`, ruff, mypy, the import-linter layer contracts and pytest, whose
integration tests start a throwaway Postgres and Redis through Testcontainers, so Docker must be
running; `frontend` runs oxlint, Vitest, the TypeScript check and the Vite build. It needs
Python 3.12+, and creates `backend/.venv` on its first run; Node.js 22 for the page. No test
needs a model key. The GitHub Actions workflow runs the backend and the frontend.

`./scripts/test.sh e2e` is opt-in: it builds amex-agent from its checkout beside this repo
(`--amex-dir` names another) and runs one full review through both agents in Docker, as its own
Compose project with its own database, since merchant memory persists across reviews and the
review relies on a database that has never seen the test statement. The development stack
publishes the same ports, so stop it first. [Testing](testing.md) states what each layer proves.

`backend/tests/test_requirements_lock.py` fails until `backend/requirements.txt` matches
`backend/pyproject.toml` and the image; `tools/lock.sh` brings it back in line.

## Deployment scripts (`scripts/`)

Docker runs the stack; `deploy.sh` and `docker-helper.sh` stop when it is not reachable.

- [`deploy.sh`](../scripts/deploy.sh) — builds the images, starts Postgres (with its schema
  migration), Redis, the manager replicas and the nginx edge in Docker, and returns once the
  manager answers through the edge. It prints this agent's Google client id, which a card agent's
  operator registers it as a caller with. Then open http://localhost:8010 and sign in with a
  Google account listed as a test user.
- `deploy.sh --ec2` — deploys to an EC2 instance in the account of `aws-config.sh`. The stack is a
  host, with an instance of its own, while `EC2_HOST_STACK` of `params.sh` is blank. Set to another
  Docker Compose repo's host stack, it is a guest on that instance, which is deployed first from its
  repo; `aws-config.sh` then names that stack's account and region, since a guest's stacks import
  the host stack's exports ([ADR 0008](adr/0008-any-docker-repo-can-host-the-instance.md)). It needs
  the AWS CLI, `ssh` and `curl`. It creates or updates this repo's CloudFormation stack of
  [`template-ec2.yaml`](../scripts/template-ec2.yaml) (the edge's port on the instance and a
  CloudFront distribution), builds the images here for ARM, loads them into the instance's Docker
  daemon over SSH and starts the stack there with
  [`docker-compose.ec2.yml`](../docker-compose.ec2.yml), and prints the CloudFront address to open
  and to register with Google ([Sign-in](sign-in.md#setting-up-google)). The git branch selects the
  stack: `main` deploys `home-finance-agent`, any other branch `home-finance-agent-fb`, a guest on
  the host's `-fb` instance; an exported `STACK_NAME` wins. Every deploy, host or guest, also makes
  sure the instance has a 1 GB swap file (`prepare_ec2_host` in `lib/ec2.sh`), so a burst beyond the
  instance's 2 GB of memory slows the stacks instead of killing a container.
- [`docker-helper.sh`](../scripts/docker-helper.sh) — `--stop [--volumes]`,
  `--logs [-e] [service...]` or `--ps` for the stack; `--volumes` also removes the database.
  With `--ec2` as its first argument it acts on the instance, and `--ec2 --delete-stack`
  deletes this repo's EC2 stack.
- [`test.sh`](../scripts/test.sh) — the quality gate and the e2e, above.
- [`init-env.sh`](../scripts/init-env.sh) — creates the settings files, the registries and the
  budget, above; `--force` replaces the settings files, hand-filled keys included.
- `tools/` — hands-on tools: [`add-card-agent.sh`](../scripts/tools/add-card-agent.sh)
  (connects a card agent, or replaces its entry, in the registry of this machine or, with
  `--ec2` first, of the instance), [`sql-helper.sh`](../scripts/tools/sql-helper.sh) (psql on
  the stack's database: a shell, `-c`, a SQL file, row counts and rows of every table, and
  `--backup <file>` and `--restore <file>` of the whole database; `--ec2` first acts on the
  instance) and [`lock.sh`](../scripts/tools/lock.sh) (recompiles `backend/requirements.txt`
  inside the Dockerfile's Python image; run it after editing the dependency list).
  [`tools/README.md`](../scripts/tools/README.md) lists them.

`scripts/common.sh` holds what the scripts share: the repo paths, the help printer, the loader
of the settings files, the registries' paths, Compose access, and the backend virtualenv setup.
`lib/settings-guard.sh` keeps the gitignored files' values out of git, and `lib/ec2.sh` holds
the EC2 target: the stack's deploy, the SSH connection with an EC2 Instance Connect key, and
Compose pointed at the instance's Docker daemon. Both, the template and the pre-commit hook are
the same files in every Docker Compose repo.

Compose runs on this machine against the instance's daemon, so nothing in the stack is
bind-mounted from this machine: the edge's `nginx/default.conf` is baked into a small image of
its own, the budget into the manager's image, and the registry reaches the manager as a Compose
secret whose content the scripts read from the registry file and Compose copies into the
container when it creates it. `docker-compose.ec2.yml` names the instance's registry for it.

`docker-helper.sh --ec2 --delete-stack` deletes this repo's EC2 stack after asking for its name:
its port on the instance and its distribution. Its containers and the database volume stay on
the instance, so run `docker-helper.sh --ec2 --stop` (with `--volumes` to drop the data) first;
`tools/sql-helper.sh --ec2 --backup <file>` keeps a copy of the data on this machine.

The IAM user of `aws-config.sh` needs to create and delete the stack's resources
(CloudFormation, security group rules, CloudFront distributions), to update the host stack's SSH
rule, and `ec2-instance-connect:SendSSHPublicKey` for the SSH connection. No IAM user has these
by default; an administrator has them all.

## Addresses

Each service has a port inside the Compose network, where the services reach each other by name;
the edge and Postgres are also published on this machine. As shipped in
`scripts/lib/stack-params.sh`:

| Service | On this machine | Inside the Compose network |
|---|---|---|
| Edge | `http://localhost:8010` (`EDGE_HOST_PORT`), on every interface: the page at `/`, `/health`, `/ready`, `/api` | `edge:8010` |
| Manager replicas | not published; reached through the edge | `manager:8010` |
| Postgres | `127.0.0.1:5434` (`DB_HOST_PORT`), for `tools/sql-helper.sh`, a psql or a manager run on the host | `db:5432` (`DB_PORT`) |
| Redis | not published | `redis:6379` |

A published port must be free on this machine; change it in `stack-params.sh` if it is not. A
new `EDGE_HOST_PORT` needs the same change in the Google client's authorized JavaScript origin
([Sign-in](sign-in.md#setting-up-google)). On the EC2 instance the edge is published at
`EC2_ORIGIN_PORT`, the same port, where only CloudFront reaches it.

## Connecting a card agent

The card agent's operator deploys it from its own repo and registers this agent as a caller with
the Google client id `deploy.sh` prints. The registration prints four values, which they send by
whatever channel the two operators share, a message or a password manager; nothing in either
agent transmits them. Each goes into one flag:

| Value | Flag |
|---|---|
| the card agent's name | `--name` |
| the URL this agent calls it at | `--url` |
| the URL your browser opens its pages at | `--browser-url` |
| the secret, shown once and confidential | `--secret` |

```bash
./scripts/tools/add-card-agent.sh --name <name> --url <url> --browser-url <browser url> \
  --secret <secret>
./scripts/deploy.sh      # the manager reads the registry at startup
```

The manager calls the URL a card agent's card advertises, which must be reachable from the
manager's container: a card agent on the same machine is `http://host.docker.internal:<port>`.
On the EC2 instance the card agents run beside this stack and keep that address, but a person's
browser opens their pages at their CloudFront addresses, which their own `deploy.sh --ec2`
prints. The instance's registry holds those, written with `--ec2` first:

```bash
./scripts/tools/add-card-agent.sh --ec2 --name amex --url http://host.docker.internal:8020 \
  --browser-url https://<amex-agent's distribution>.cloudfront.net --secret <secret>
./scripts/deploy.sh --ec2
```

## Running the agent on the host

For fast restarts and a debugger, the manager can run as a process on this machine against the
stack's Postgres, with the edge and the replicas stopped so the process takes port 8010. Run it
from the repo root, where it reads the settings files and `config/budget.yaml`:

```bash
./scripts/deploy.sh                                   # Postgres on 127.0.0.1:5434, migrated
bash -c 'source scripts/common.sh && compose stop edge manager'
(cd frontend && npm ci && npm run build)
HFM_FRONTEND_DIST=frontend/dist LANGGRAPH_STRICT_MSGPACK=true backend/.venv/bin/uvicorn \
  hfm.platform.app:create_app --factory --port 8010 --timeout-graceful-shutdown 5
```

The process has no Redis (`REDIS_URL` is unset), so its in-process bus carries every review's
events. It reads `backend/card-agents.yaml`, whose `host.docker.internal` addresses name this
machine from inside a container only; for a review from the host, write a registry of
`http://localhost:<port>` addresses with `tools/add-card-agent.sh --file <path>` and export
`CARD_AGENTS_FILE=<path>` before starting the process. `./scripts/deploy.sh` brings the edge and
the replicas back.
